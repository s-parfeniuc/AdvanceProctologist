# Notation contract

Every symbol, name and definition used in `notes/` is fixed here, and every
entry was read off a **rendered page** in `build/pages/`, never off
`build/text/`. Each rule cites the page that establishes it, so any rule can be
re-checked in one step.

Where an external source (Aho et al., Scott, Mitchell, GHC documentation) uses
different notation, **the lecture material wins** and the external form is
introduced only as a clearly labelled aside. See [§7](#7-when-external-sources-disagree).

## 0. The two arrows

The single most important rule, because both forms appear in the same chapter
and they are not the same thing:

| Form | Meaning | Where |
|---|---|---|
| `→` `⇒` | grammar productions and derivations — metatheory | ch.02, ch.03 |
| `->` `=>` | Haskell/Rust/Java source code, verbatim as the slides write it | ch.05, ch.07–ch.13 |

Never "tidy" `->` into `→` inside a code block, and never write a production
with ASCII `->`. In Haskell, `->` is the function type constructor and `=>` is a
class constraint [Haskell-TypeClasses p.19]; in a grammar, `→` separates the two
sides of a production [Parsing p.4].

## 1. Grammars

*Source: `03-AP-25-09-25-Parsing.pdf` pp.4–6, 9.*

A **grammar** is a 4-tuple **G = (N, T, P, S)** where [Parsing p.4]

- `T` is a finite set of tokens (*terminal* symbols)
- `N` is a finite set of *nonterminals*
- `P` is a finite set of *productions* of the form `α → β`
  where `α ∈ (N∪T)* N (N∪T)*` and `β ∈ (N∪T)*`
- `S ∈ N` is a designated *start symbol*

> The component order is **N before T**. Aho et al. and most textbooks write
> `G = (T, N, P, S)` or `(V, T, P, S)`; the slides do not. Use `(N, T, P, S)`.

Also on that slide:

- `A*` is the set of finite sequences of elements of `A`.
  If `A = {a,b}` then `A* = {ε, a, b, aa, ab, ba, bb, aaa, …}`
- `AB = {ab | a ∈ A, b ∈ B}`

### Metavariables

*Verbatim from the deck's own "Notational Conventions Used" slide
[Parsing p.5].* These are binding for ch.02 and ch.03.

| Class | Metavariables | Range | Specific examples given |
|---|---|---|---|
| Terminals | `a, b, c, …` | `∈ T` | `0`, `1`, `id`, `+` |
| Nonterminals | `A, B, C, …` | `∈ N` | `expr`, `term`, `stmt` |
| Grammar symbols | `X, Y, Z` | `∈ (N∪T)` | |
| Strings of terminals | `u, v, w, x, y, z` | `∈ T*` | |
| Strings of grammar symbols | `α, β, γ` | `∈ (N∪T)*` | |

Two metavariables are used but not listed on the conventions slide:

- `δ` — a fourth string of grammar symbols, from [Parsing p.9] onward
- `η` — the string after `A` in the left-recursion test `A ⇒⁺ A η` [Parsing p.40]

Derived nonterminals introduced by grammar transformations are written with a
subscript `R`: `A_R` in the left-factoring and left-recursion-elimination rules
[Parsing pp.39–40], and `E_R`, `T_R`, `S_R` in the worked tables
[Parsing pp.53, 56]. The one exception is the pasted Aho et al. figure on
[Parsing p.42], which uses primes (`E'`, `T'`) for the same nonterminals. Use the
subscript form outside that figure.

Specific nonterminals are set in *italics* (`expr`), specific terminals in
**bold** (`id`). Reproduce that distinction.

**Spelling: "nonterminal"**, one word, no hyphen — the slides and Aho et al.
agree. The existing lecture `.md` files write "non-terminal"; that is corrected.

### Grammar classification

[Parsing p.6] A grammar `G` is said to be

- **Regular** if *right linear*, every production `A → w B` or `A → w`;
  or *left linear*, every production `A → B w` or `A → w`  (`w ∈ T*`)
- **Context free** if every production is `A → α`, where `A ∈ N` and `α ∈ (N∪T)*`
- **Context sensitive** if every production is `α A β → α γ β`,
  where `A ∈ N`, `α, γ, β ∈ (N∪T)*`, `|γ| > 0`
- **Unrestricted**

[Parsing p.7] Two different `L`s appear and must be kept apart:

- `L(G)` — the language generated by the grammar `G`
- `ℒ(T)` — script L, the *class* of languages of grammar type `T`,
  `ℒ(T) = { L(G) | G is of type T }`

Inclusion is `⊂`:

    ℒ(regular) ⊂ ℒ(context free) ⊂ ℒ(context sensitive) ⊂ ℒ(unrestricted)

The examples on that slide set terminals in bold: `L₁ = { aⁿbⁿ | n ≥ 0 }` is
context free, `L₂ = { aⁿbⁿcⁿ | n ≥ 0 }` is context sensitive, and every *finite*
language is regular.

## 2. Derivations

*Source: [Parsing p.9]. Reproduce these exactly — this slide is the one whose
extracted text is worst corrupted.*

A **one-step derivation** is defined by

    γ α δ  ⇒  γ β δ        where α → β is a production in the grammar

- `⇒` is **leftmost** `⇒ₗₘ` if `γ` does not contain a nonterminal
- `⇒` is **rightmost** `⇒ᵣₘ` if `δ` does not contain a nonterminal
- **Transitive closure** `⇒*` (zero or more steps)
- **Positive closure** `⇒⁺` (one or more steps)

`α` is a **sentential form** if `S ⇒* α`.

The **language generated by G**:

    L(G) = { w ∈ T* | S ⇒⁺ w }

> Two things not to "fix". The slide labels `⇒*` the *transitive* closure
> although zero-or-more steps makes it the reflexive-transitive closure; keep
> the slide's wording. And `L(G)` is defined with `⇒⁺`, not `⇒*`; keep that too.

Subscripts render as `⇒ₗₘ` / `⇒ᵣₘ` in prose and as `=>lm` / `=>rm` only inside
code blocks where subscripts are unavailable.

## 3. FIRST and FOLLOW

*Source: [Parsing pp.37, 44, 45]. Set-builder braces, the `\` difference
operator and `∅` are all as the slides write them.*

**FIRST** [Parsing p.44]

    FIRST(α) = { the set of terminals that begin all strings derived from α }
    FIRST(a) = {a}                       if a ∈ T
    FIRST(ε) = {ε}
    FIRST(A) = ∪(A→α) FIRST(α)           for A → α ∈ P

The deck defines FIRST twice with different wording. [Parsing p.37] says "the set
of terminals that appear as the first symbols of **one or more** strings generated
from `α`"; p.44 above says "begin **all** strings". The p.37 reading is the
correct one — p.44's phrasing is loose and must not be quoted as the definition
without the p.37 gloss.

**FOLLOW** [Parsing p.45]

    FOLLOW(A) = { the set of terminals that can immediately follow nonterminal A }

    FOLLOW(A) =
        for all (B → α A β) ∈ P do
            add FIRST(β)\{ε} to FOLLOW(A)
        for all (B → α A β) ∈ P and ε ∈ FIRST(β) do
            add FOLLOW(B) to FOLLOW(A)
        for all (B → α A) ∈ P do
            add FOLLOW(B) to FOLLOW(A)
        if A is the start symbol S then
            add $ to FOLLOW(A)

`$` is the end-of-input marker. Keyword-like tokens in the slides' pseudocode
(`for all`, `do`, `if`, `then`, `add … to …`) are set **bold** on the slide;
in the notes they live in code blocks and need no extra markup.

**LL(1)** [Parsing p.46] — a grammar `G` is LL(1) if it is not left recursive
and for each collection of productions `A → α₁ | α₂ | … | αₙ` the following
holds:

1. `FIRST(αᵢ) ∩ FIRST(αⱼ) = ∅` for all `i ≠ j`
2. if `αᵢ ⇒* ε` then
   - a. `αⱼ ⇏* ε` for all `i ≠ j`
   - b. `FIRST(αⱼ) ∩ FOLLOW(A) = ∅` for all `i ≠ j`

Note `⇏*` (negated derivation) in 2.a.

## 4. Types and polymorphism

*Source: `15-AP25-10-27-Types-Polymorphism.pdf`. This deck has fault **C**
(`applica4on`); every term below was read off the render.*

Definitions [Types p.5] — a programming language is

- **strongly typed** if no type error (*type clash*) can occur: application of
  an operation to a value not supporting such operation
- **statically typed** if (most) type checking is performed at compile time
- **dynamically typed** otherwise

The **classification of polymorphism** [Types p.14] is the Cardelli–Wegner
tree, with the deck's own vocabulary: *Universal* splits into **Coercion**,
**Parametric** and **Inclusion**; *Parametric* into **Implicit** and
**Explicit**, and *Explicit* further to **Bounded**, annotated
**Covariant / Invariant / Contravariant**; *Ad hoc* splits into **Overriding**
and **Overloading**. The tree is reproduced as a cropped figure rather than
re-drawn, so its edges cannot be misread.

Spell it **"Ad hoc"** (two words, as the slide), not "ad-hoc".

## 5. Java

*Sources: `16-AP25-JavaGenerics.pdf`, `24-AP25-JLambdas.pdf`,
`25-AP25-Reflection_Annotations_in_Java.pdf`. Decks 16 and 25 carry fault **C**.*

- **Subtyping: `S <: T`, glossed on first use.** The Types deck introduces the
  symbol explicitly — "methods/functions with a formal parameter of type **T**
  accept an actual parameter of type **S <: T** (**S** subtype of **T**)"
  [Types p.20]. The Generics deck then works in prose instead ("Integer is
  subtype of Number", "`List<Number>` is neither a supertype nor a subtype of
  `List<Integer>`"). Use `<:` where a relation is being stated compactly and
  prose where the deck reasons in prose; both are the lecture's own usage.
- Variance vocabulary is **covariant / contravariant / invariant**, with the
  deck's safety rules: "covariance is safe if the type is read-only",
  "contravariance is safe if the type is write-only".
- Java source, generic parameters (`<T>`, `<? extends Number>`) and annotation
  syntax (`@Override`) are reproduced verbatim.

## 6. Haskell

*Sources: `17-AP25-Haskell-TypeClasses.pdf`, `21-AP25-Monads.pdf`.*

Code is verbatim slide text: `::` for signatures, `->` for function types, `=>`
for class constraints, `class C a where` / `instance C T where`
[Haskell-TypeClasses p.19]. Type variables follow the decks: `a`, `n`, `w`, `t`,
and `m` for a type constructor.

The **Monad** class as the deck defines it [Monads p.~26 of `build/text` line 376]:

```haskell
class Monad m where             -- definition of Monad type class
        return :: a -> m a
        (>>=)  :: m a -> (a -> m b) -> m b   -- "bind"
        (>>)   :: m a -> m b -> m b          -- "then"
```

> This is the pre-2015 `Monad` class. Modern GHC makes `Applicative` a
> superclass of `Monad` and defines `return = pure`. The notes use the deck's
> form and flag the divergence in an aside where it matters — they do not
> silently modernise it, because the exam is on this material.

The eqtype build-up in the overloading motivation is kept in the deck's own
notation, including `a(==)` and SML's `''a` [Haskell-TypeClasses pp.10–11].

## 7. When external sources disagree

Order of authority:

1. the lecture deck for the chapter
2. the existing lecture `.md` transcripts, for lectures with no deck (00–02, 04)
3. the `DOCS/` textbook chapter listed as *supporting* for that chapter
4. anything else

Applying rule 1 over rule 3 gives the concrete divergences already found:

| Topic | Notes use (lecture) | External form (not used) |
|---|---|---|
| Grammar tuple | `G = (N, T, P, S)` [Parsing p.4] | `G = (T, N, P, S)`, `(V, Σ, R, S)` |
| Java subtyping | prose, "is subtype of" | `Integer <: Number` (Mitchell) |
| Monad class | `return`, `>>=`, `>>` | `pure`, `Applicative` superclass (GHC ≥ 7.10) |
| `⇒*` | "transitive closure" | reflexive-transitive closure |

Where an external source is genuinely needed to make a slide comprehensible —
which is the normal case for Aho et al. ch.4 filling in the parsing
algorithms — it is cited explicitly and its notation is translated into the
table above before use.

## 8. Chapter conventions

- Cite by **PDF page**: `[Parsing p.45]`. Printed slide numbers drift; see
  `SOURCES.md`.
- Definitions taken verbatim from a slide go in a blockquote opening
  `> **Definition (name).**` and carry a citation.
- Notes are in **English**. The Parsing deck contains pasted Italian textbook
  excerpts (e.g. [Parsing p.8]); these are translated, with the fact noted.
- Figures are cropped page renders in `notes/assets/`, named
  `fig-<source>-p<page>-<slug>.png`, produced by `scripts/crop.sh`. Nothing is
  re-drawn.
- Run `scripts/check-notation.sh` before considering a chapter done. It fails on
  any surviving `®`, `Î`, `È`, `Þ`, `ﬁ`, `ﬂ`, `applica4on`-style residue, `【`
  transcript marker, or broken image embed.
